Academic Project 2025 – 2026

Sistem Reservasi Aurora Beauty Salon

Web-based reservation information system with a two-stage transaction flow: 50% down payment (DP) upon booking, and final payment after the service is completed. Each payment stage undergoes admin verification, and customers must check-in upon arrival at the salon before the service begins.

Technical Insight: Based on the users table structure (columns two_factor_secret, remember_token), this system is built on Laravel with Jetstream/Fortify auth scaffolding — highly relevant for testing cookie-based sessions and 2FA features.

Page Object Model — every locator lives once in pages/, reused across all test files.

Reused login session — customer login runs once in auth.setup.js, saved as Playwright storageState and reused by every test that needs an authenticated customer.

Isolated test data — a dedicated, idempotent customer account is seeded via a PHP script that never touches real customer rows.

DOM-based assertions — checks like "grid finished loading" assert on element structure/count, not on placeholder text, so tests don't break when the active language changes.

Self-cleaning test data — registration and full-flow tests create a uniquely-emailed account per run and delete it in afterEach via a small PHP helper, so the dev database never accumulates leftover test accounts.

Newest coverage: full Booking → Payment E2E (Group K)

The suite now drives the entire funnel with a single, disposable test account: register → verify email (via DB) → login → pick a category & service → choose a schedule → checkout → pay → success page → booking history, asserting the final reservation shows up as is_lunas: true.

Payment strategy: the app's Midtrans integration runs on real sandbox credentials. The test captures the Snap token from the app's own /booking/midtrans/proses endpoint, waits for the genuine Snap iframe to open and asserts it's served from sandbox.midtrans.com — proving the integration is really wired up — then completes the transaction by calling /booking/midtrans/callback directly, the same endpoint Snap.js's own success callback calls in production. Snap's payment-method UI is a third-party widget that renders non-deterministically between runs, so this still exercises the app's real backend logic (validation, status update, response) without depending on a flaky third-party UI.

Finding — test assumption vs. product bug: on the first run, 2 of 41 tests failed. Investigation showed config/app.php hardcodes 'locale' => 'id' instead of reading env('APP_LOCALE'), so the app always defaults to Indonesian regardless of .env. The app's own behavior was consistent — only my test's expectation was wrong. Fixed on the test side with a single DEFAULT_LOCALE constant, without touching application code, and reported the distinction explicitly.

QA Learnings & Notes

State Inconsistency

The two-stage payment flow (DP → Final) is prone to state inconsistency if admin verification is missed — crucial to ensure reservation status cannot "skip" to the next phase.

Employee Involvement

Employees are not system actors, so validating "service provided" relies on manual admin/system input — a critical point worth testing with negative scenarios.

Double Booking

Double booking prevention on time slots is a critical area, especially for concurrent request scenarios (two customers booking the same slot simultaneously).
